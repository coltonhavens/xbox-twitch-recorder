PUBLIC APPLICATION INFORMATION

Privacy policy

Xbox Twitch Recorder · Last updated November 1, 2026

Phase 1: information website only.

The recording automation is planned and has not been implemented as part of this phase. This website does not offer account connection, request OAuth permissions, collect authentication tokens, download broadcasts, or upload files to Google Drive.

1. Who this project is for

Xbox Twitch Recorder is a personal application maintained by the owner of the coltonhavens/xbox-twitch-recorder repository. Its intended purpose is to archive the owner’s completed Xbox gameplay broadcasts from Twitch into the owner’s Google Drive. It is not currently offered as a public service.

2. Data handled by this website today

The site serves static public pages through Firebase Hosting. It has no forms, account system, analytics, advertising, tracking pixels, embedded third-party media, or application cookies or browser storage. It does not deliberately collect visitor profile information.

Requests to the hosting provider necessarily include technical information such as IP address, requested URL, browser information, and request time. Google may process technical and operational information to deliver and maintain Firebase Hosting under its own policies. This project does not specify a separate retention period for provider-managed records. See Google’s Privacy Policy and Firebase privacy information. Following external links sends you to services with their own privacy practices.

3. Planned Twitch access

A future backend would use the Twitch API to identify the owner’s channel and retrieve broadcast metadata, such as video identifiers, titles, creation times, durations, and availability. Where permitted and technically available, it would retrieve completed VOD video for archiving. Exact API permissions and the video retrieval method have not yet been finalized.

Recordings may contain gameplay, microphone audio, voices, usernames, or other information already included in the broadcast. Only audio present in the available VOD could be preserved; missing or muted audio cannot be restored. Twitch settings, rights restrictions, and VOD expiry may prevent retrieval. This phase does not collect chat separately or record live sessions.

4. Planned Google OAuth permissions and Drive uploads

The intended Google integration would use OAuth 2.0 so the owner can authorize uploads without giving the application their Google password. It would use authorization only to create and manage archive files needed for this purpose in the owner-designated Drive folder. This website does not expose that folder or provide access to its contents.

The exact scopes granted to the existing OAuth application have not been verified by this website implementation. A future implementation should request the minimum permissions it needs. The per-file scope https://www.googleapis.com/auth/drive.file is a planned option, not a claim about current configuration; access to an existing folder must be supported through an appropriate authorization or selection flow. Knowing a folder ID alone grants no access. Broader Drive access must not be assumed or silently requested. The consent screen at authorization time will describe the permissions actually requested.

Intended Google user data includes authorization tokens, the chosen folder identifier, uploaded video files, file names, and resulting Drive file identifiers and upload status. Unrelated Drive files, Gmail, and contacts are not needed for the intended archive workflow. Google user data would be used only for the owner-authorized archive function, not sold, used for advertising, or used to train generalized AI models.

5. Planned processing, temporary files, and tokens

Future cloud processing would require temporary video files or video segments while retrieving and uploading recordings. Job metadata may be needed to track progress, errors, and completed uploads. The storage location, retry behavior, cleanup procedure, and retention periods have not been implemented or established. This policy does not promise immediate deletion or a fixed cleanup deadline.

Unattended operation may require Google and Twitch access tokens and, where issued, refresh tokens. These grant account access within the permissions authorized. No token storage backend or specific encryption configuration is implemented by this static site. Before automation is enabled, token handling, restricted backend access, retention, and cleanup need to be implemented and documented. Credentials and tokens must never be included in public website files, source control, or public issue reports.

6. Providers and data sharing

The planned workflow would involve Twitch as the broadcast source, Google Drive as the archive destination, and a cloud processing provider to be finalized. Google Cloud is the intended platform for that future processing; this phase configures Firebase Hosting only. Necessary recording content and metadata would pass through those services for retrieval, processing, and upload. The service is not intended to sell personal data or share recordings with advertisers.

Drive file access would depend on the owner’s folder and file sharing settings. Uploading a file does not by itself establish that it is private. The owner should review sharing settings before archiving content.

7. Retention, control, and revocation

There are no application accounts, stored OAuth tokens, or processed recordings created by this website. For the future service, archive files would remain in the owner’s Drive until the owner deletes them or otherwise manages them through Google Drive. Temporary files, job records, logs, and stored tokens will need explicit retention and deletion procedures before operation; no fixed periods are currently defined.

  • Review and revoke Google access at Google Account connections.
  • Review and disconnect authorized Twitch applications at Twitch Connections.
  • Manage recording access and delete archived files directly in Google Drive, including its Trash, according to Google’s deletion behavior.
  • When a backend exists, disable its scheduled jobs and remove stored credentials and temporary data using its documented administration procedure.

Revoking access prevents future authorized API access once revocation takes effect. It does not automatically delete existing Drive files, temporary copies, or previously stored job data, and cannot recall data already downloaded. A future backend must handle revoked or expired authorization without continuing unauthorized access.

8. Security and future changes

This phase contains public static files only. It does not establish backend security controls or guarantee that future processing will be risk-free. Before enabling automation, this policy must be reviewed against the actual scopes, providers, token storage, logging, retention, and deletion behavior. Material changes will be reflected here with a revised update date before the new processing begins.

9. Contact

Contact the project maintainer through the repository’s issue tracker for policy questions. Issues may be public: do not include private recordings, credentials, tokens, or personal account details. No private support email has been designated for this phase.
