PUBLIC APPLICATION INFORMATION

Privacy policy

Xbox Twitch Recorder · Last updated November 1, 2026

Phase 1: information website only.

Recording worker source is prepared for review, but cloud recording and account authorization are not active. This website does not offer account connection, request OAuth permissions, collect authentication tokens, download broadcasts, or upload files to Google Drive.

1. Who this project is for

Xbox Twitch Recorder is a personal application maintained by the owner of the coltonhavens/xbox-twitch-recorder repository. Its intended purpose is to archive the owner’s saved Xbox gameplay broadcasts from Twitch into the owner’s Google Drive. It is not currently offered as a public service.

2. Data handled by this website today

The site serves static public pages through Firebase Hosting. It has no forms, account system, analytics, advertising, tracking pixels, embedded third-party media, or application cookies or browser storage. It does not deliberately collect visitor profile information.

Requests to the hosting provider necessarily include technical information such as IP address, requested URL, browser information, and request time. Google may process technical and operational information to deliver and maintain Firebase Hosting under its own policies. This project does not specify a separate retention period for provider-managed records. See Google’s Privacy Policy and Firebase privacy information. Following external links sends you to services with their own privacy practices.

3. Planned Twitch access

The prepared scheduled recorder uses public Twitch broadcast listings and playback metadata to find completed saved broadcasts for the owner’s channel, then uses a video downloader to retrieve available full VOD video and audio. The official metadata API is not treated as a video download endpoint. This implementation is not deployed, and download compatibility with the owner’s test VOD has not yet been independently verified.

Recordings may contain gameplay, microphone audio, voices, usernames, or other information already included in the saved broadcast. The owner confirmed microphone audio in a saved test broadcast. Future videos may have different audio availability; missing, muted or excluded audio cannot be restored. VOD expiry, processing and playback restrictions can prevent archiving. The proposed job does not record live playback or collect chat separately.

4. Planned Google OAuth permissions and Drive uploads

The intended Google integration would use OAuth 2.0 so the owner can authorize uploads without giving the application their Google password. It would use authorization only to create and manage archive files needed for this purpose in the owner-designated Drive folder. This website does not expose that folder or provide access to its contents.

The prepared recorder requests only the per-file scope https://www.googleapis.com/auth/drive.file. This permits access to app-created files and files or folders the owner explicitly selects through Google Picker. The local authorization helper asks the owner to select the existing archive folder and verifies that it is writable. Knowing a folder ID alone grants no access. The existing Google project’s granted scopes have not been independently inspected, and no consent has been performed by this website. The helper rejects broader scopes; the consent screen describes the actual request.

Intended Google user data includes authorization tokens, the chosen folder identifier, uploaded video files, file names, and resulting Drive file identifiers and upload status. Unrelated Drive files, Gmail, and contacts are not needed for the intended archive workflow. Google user data would be used only for the owner-authorized archive function, not sold, used for advertising, or used to train generalized AI models. Use and transfer of Google API data would follow the Google API Services User Data Policy, including its Limited Use requirements.

5. Planned processing, temporary files, and tokens

Future cloud processing would require temporary video files or video segments while retrieving and uploading recordings. Job metadata may be needed to track progress, errors, and completed uploads. The proposed GitHub Actions job streams a full MP4 to Google Drive without saving the whole video on its temporary runner disk. A small recovery manifest in the owner’s Drive records video identifiers, checksums, file identifiers and completion to prevent duplicates. Temporary process files are cleaned after each attempt; incomplete uploads may require another source download. No recording automation has been activated. This policy does not promise immediate deletion or a fixed cleanup deadline.

The prepared unattended workflow uses a Google OAuth refresh configuration stored as an encrypted GitHub Actions secret, available only to the gated recording job. Short-lived access tokens and upload-session identifiers are handled in memory and are not intentionally written to logs, source control, artifacts, or caches. A proposed temporary HTTPS authorization service would keep refresh credentials server-side while the owner grants access in a browser, seal the configuration for GitHub’s encrypted secret API, and discard its connection session afterward. It would read the connected Drive account’s email only to confirm the configured owner, using the existing per-file permission rather than an additional sign-in scope. Hosting that service requires separate owner approval; it is not deployed. Public Twitch playback does not initially require the owner’s Twitch password or login token. This describes the prepared design, not an active account connection or an independently audited security guarantee. Credentials must never be included in public website files, issue reports, or chat.

6. Providers and data sharing

The planned workflow would involve Twitch as the broadcast source, Google Drive as the archive destination, GitHub-hosted Actions runners for processing, and an owner-approved temporary authorization host for one-time setup. A Render Free service is proposed for that setup only, not provisioned. Firebase Hosting serves the separate static website; recording does not require Google Cloud compute or storage. Necessary recording content and metadata would pass through those services for retrieval, processing, and upload. The service is not intended to sell personal data or share recordings with advertisers.

Drive file access would depend on the owner’s folder and file sharing settings. Uploading a file does not by itself establish that it is private. The owner should review sharing settings before archiving content.

7. Retention, control, and revocation

There are no application accounts, stored OAuth tokens, or processed recordings created by this website. For the future service, archive files would remain in the owner’s Drive until the owner deletes them or otherwise manages them through Google Drive. The prepared recovery manifest remains in the owner’s Drive until the owner removes it; deleting it can prevent duplicate-upload recovery. The stored refresh configuration remains in the repository’s encrypted Actions secret until the owner removes or replaces it. Temporary process files are cleaned after an attempt and ephemeral runners are discarded after jobs; abrupt termination may interrupt cleanup. Workflow logs follow the repository’s configured retention. No fixed log retention or immediate provider deletion guarantee is asserted.

  • Review and revoke Google access at Google Account connections.
  • Review and disconnect authorized Twitch applications at Twitch Connections.
  • Manage recording access and delete archived files directly in Google Drive, including its Trash, according to Google’s deletion behavior.
  • To stop the prepared recorder, disable its workflow, remove the stored Actions authorization secret, and revoke the Google grant. Manage archive and recovery files separately in Google Drive; revocation does not delete them.

Revoking access prevents future authorized API access once revocation takes effect. It does not automatically delete existing Drive files, temporary copies, or previously stored job data, and cannot recall data already downloaded. A future backend must handle revoked or expired authorization without continuing unauthorized access.

8. Security and future changes

This website contains public static files only. The repository also contains an inactive recording workflow and authorization helper; neither means the owner’s account has been connected or that processing is risk-free. Before enabling automation, this policy must be reviewed against the actual scopes, providers, token storage, logging, retention, and deletion behavior. Material changes will be reflected here with a revised update date before the new processing begins.

9. Contact

Contact the project maintainer through the repository’s issue tracker for policy questions. Issues may be public: do not include private recordings, credentials, tokens, or personal account details. No private support email has been designated for this phase.
