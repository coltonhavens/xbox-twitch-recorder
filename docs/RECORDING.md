# Live recording implementation and rollout proposal

Status: implementation prepared; NOT provisioned or operational. Offline core tests pass. Twitch, Drive, dependency installation, systemd installation, and cloud acceptance are unverified. Keep RECORDING_ENABLED=false until owner approval and acceptance checks below. No website login is added.

## Recording method

Xbox → Twitch **live playback HLS** → Streamlink stdout → FFmpeg stream copy → five-minute MPEG-TS chunks → owner-authorized Drive folder. This does not use Twitch VODs. The chosen live rendition contains the audio Twitch serves to live viewers; FFmpeg maps its video and available audio without transcoding. It cannot restore an Xbox microphone excluded from the broadcast, party chat without consent/settings, missing source packets, advertisements, or Twitch restrictions. An audio track alone does not prove it contains speech. Streamlink's Twitch plugin relies on playback endpoints and can break independently of the supported Helix metadata API. Do not bypass access restrictions; a failed plugin is an operational incident.

## Cloud worker and storage

Propose ONE non-Spot Compute Engine VM, initially e2-small, Debian 12, with 100 GiB persistent balanced disk mounted at /var/lib/xtr, auto-delete disabled. This is a proposal, not a sizing guarantee. Increase CPU/memory only after measuring Streamlink/FFmpeg memory and throughput. No inbound application ports or public web endpoint. Operator access through approved IAP/OS Login, not public SSH. Single VM is deliberate: SQLite WAL and flock provide one-writer behavior; do not horizontally scale this implementation or attach cloned disks to simultaneous workers. Long streams use bounded chunks, not a whole stream in RAM or a request with a runtime limit. A VM avoids Cloud Run request lifetime and ephemeral filesystem constraints.

Use an approved outbound path; public egress or Cloud NAT both need review and may cost money. Worker service account must be separate from github-hosting-deploy, with no project Editor/Owner. If using Secret Manager, grant secretAccessor only on the two specific secrets (Twitch client secret and owner Drive refresh credentials); bootstrap uses attached VM identity, no SA private keys. Logging/Monitoring writer permissions, enabled APIs, network/IAP roles, alerts, persistent disk and VM creation each require approval. No Terraform apply or gcloud create is included or executed.

Provisioning operator installs Python 3.11+, ffmpeg/ffprobe, creates OS user xtr, copies source to /opt/xtr, creates a venv and installs recorder/requirements.txt, mounts the durable disk, and sets ownership to xtr. Review package pins against current releases; install and playback compatibility have not been tested here. Copy deploy/recorder.service and deploy/worker.env.example to /etc/systemd/system and /etc/xtr/worker.env. Restrict secret files to xtr, mode 0600, outside source and public/. Never place credentials into startup-script metadata, command arguments, logs, or the website. Start only after approval. Do not run the worker on a developer laptop as the production solution.

## Detection, interruptions, and reliability

Poll Helix Get Streams for exactly TWITCH_USER_ID every 30 seconds; application access tokens are acquired using a Twitch app client credential, refreshed on expiration or after 401. No broadcaster user scope is required for public live metadata. A poll can miss a very short stream and normally loses up to the polling/startup delay at the beginning. Helix metadata does not grant playback access. Transient API failures retry after 30 seconds; API failures never mean a stream has ended. At this one-channel rate API quota should be modest; monitor 429s and actual current rate limits before rollout. EventSub could reduce start delay later but is not implemented.

Capture runs while Streamlink/FFmpeg deliver data, independently of metadata polling. Playback timeout exits and the next successful live poll starts a new capture attempt. Each attempt has a UUID and Twitch stream ID. Segment files are named by attempt and sequence. Reconnects can produce short playback overlap and gaps; this implementation prevents duplicate **uploads of a chunk**, not repeated media frames across reconnects. It does not promise gapless capture or reconstruct missing periods. Record interruption times from capture_start/capture_end/capture_retry logs; inspect output before claiming session completeness.

Only closed segments are moved atomically into the upload queue. After a worker crash, the next process locks the same durable disk and recovers abandoned capture directories, including a possibly incomplete last TS segment. ffprobe validates video and positive duration; absent audio generates a warning. Invalid media moves to quarantine without deletion, so one bad tail does not block subsequent uploads. Quarantine requires operator inspection and removal after review. Probe validity does not prove there are no glitches.

An independent uploader drains while capture continues. Each chunk has a SHA-256 and a preallocated Drive file ID persisted in SQLite before create. Resumable uploads use 8 MiB chunks, request retries and bounded HTTP timeouts. Process restarts can restart a pending transfer with the same file ID; existing objects are checked before upload. Verify Drive size, MD5, SHA appProperty and parent before marking completion and deleting local media. A crash after create but before local completion is recoverable through that stable ID. Journal completion entries remain for audit. No automatic deletion from Drive, sharing changes, or duplicate-name searches. Persistent resumable-session URLs are not stored; restarted processes may retransmit bytes but cannot intentionally create a second file ID for that chunk. A remote checksum conflict retains local data and requires investigation.

At <3 GiB free, new captures pause; at <2 GiB, active capture stops. Failed uploads remain on disk; storage is not infinite. Monitor free disk and backlog age and expand/resolve authorization before the disk fills. Malformed chunks are quarantined. Drive quota/auth errors retain pending media and retry every 30 seconds, with upload requests using exponential retries; no unbounded local deletion. The VM/disk remain a single failure domain, not HA. Disk loss before upload loses media. Backups/snapshots are a separately approved cost and privacy decision.

## Owner OAuth and existing Drive folder

Destination is fixed server-side to 1X9VfSes_byvkygreHfdvGNHzVXjvAYBG. Knowing this ID is not access. Consumer My Drive uploads need an owner's OAuth refresh token with offline access, not a service account with no personal storage quota. A Shared Drive design would be different and must be explicitly selected.

Worker accepts exactly drive.file. The existing folder must be authorized for this app using a Google Picker selection by the owner with the same OAuth client, or another documented per-file grant. This selection/consent bootstrap is NOT implemented; no broader drive scope is silently substituted. Before coding the browser authorization flow, inspect existing OAuth client type, consent publishing status, domain verification, and approved redirect origins. These are currently unavailable and changing them requires owner approval. Keep refresh credentials in Secret Manager and load to a restricted runtime file; an authorized_user JSON token file is sensitive but is NOT a service account JSON key. Do not share it in chat. External apps in Testing may issue refresh tokens expiring after seven days for non-basic scopes; confirm production publishing or approved internal status before unattended use. This is a launch blocker.

Startup checks folder MIME type and canAddChildren using the authorized identity. A failed startup leaves recording data queued, emits drive_unavailable, and retries. Test folder selection, upload, checksum and revocation with a small synthetic file before live capture. Do not assume the fixed folder is accessible until this succeeds.

## Costs and limits requiring a budget decision

No resources have been created. Monthly baseline: VM hourly rate × running hours (about 730 for always on), 100 GiB disk × regional disk rate, network/public IP/NAT charges as applicable, logging, secrets access and any backups. Obtain current regional prices; no dollar estimate here is a quote. Video transfer is likely the dominant variable: 6 Mb/s ≈ 2.7 GB/hour, 8 Mb/s ≈ 3.6 GB/hour plus overhead. A 100 GiB spool holds roughly a day at high bitrate, less after OS/reserve; monitor actual usage. Cloud-to-Drive traffic must not be assumed free. Budgets notify but do not cap spending. Propose alerts at 50/80/100% of the owner-selected monthly budget and operational alerts for no heartbeat >2 minutes, upload backlog >15 minutes, free disk <10 GiB, and repeated capture errors; these alerts are NOT yet installed.

Drive commonly enforces 750 GB/day upload per user and a 5 TB per-file limit, plus storage and request quotas; verify current account limits. Five-minute chunks stay far below the file limit but daily traffic and existing uploads share the user's quota. No transcoding reduces CPU cost; selected best quality determines bandwidth. Files are individual TS chunks, not a single MP4; joining/remuxing is a future optional step with extra storage/compute. User must approve this output format or request a reviewed merge pipeline before acceptance.

## Required acceptance sequence

1. Obtain cloud read access and inspect existing resources; never recreate existing SA, WIF, site, disk, app, or VM.
2. Approve region, monthly budget, VM/disk/egress, worker IAM/secrets/alerts, and OAuth setup. Apply only approved changes.
3. Install dependencies; verify Streamlink Twitch plugin compatibility. Authorize the exact Drive folder with drive.file and upload a synthetic clip. Verify checksum and final parent; revoke access and confirm local retention/retry.
4. Run the unit tests and the synthetic FFmpeg audio test on the worker. Test actual SIGTERM/restart, interrupted capture, network loss, ambiguous upload success, quota failure, disk threshold, and an extended synthetic stream. Mock tests alone are insufficient.
5. Owner performs a short Xbox broadcast with spoken microphone marker and game audio. Compare live playback, captured chunks and Drive copy by listening and probing. Confirm no separate VOD audio track assumption; evaluate party-chat settings separately. Do not mark microphone verified until heard in the final file.
6. Restart mid-stream and interrupt/reconnect Xbox. Measure missing/overlapping time and get owner acceptance of boundaries. Run a long stream, monitor resource use and costs, confirm alerts, then enable unattended operation.
