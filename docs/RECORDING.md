# Scheduled Twitch VOD → Google Drive archive

Status: draft source, NOT deployed or operational. Channel: **MrHype420**. Destination: `1X9VfSes_byvkygreHfdvGNHzVXjvAYBG`. The owner confirmed microphone audio in VOD **2917078189**; this is owner-provided evidence for that VOD, not an independent listening test or a guarantee for every future broadcast.

## Recommended inexpensive architecture

One **Cloud Scheduler** hourly trigger → authenticated **Cloud Run Job** → Twitch metadata and saved HLS playback → **one MP4** temporarily staged in a private same-region **Cloud Storage** bucket → resumable upload to the owner's existing **Google Drive**. The container exits when no work remains. No VM, systemd service, always-on live capture, persistent block disk, public website endpoint, EventSub server, or transcoding. The revised branch removes the live worker/service template.

Recommend us-central1 initially, 1 vCPU / 1 GiB memory, one task, parallelism 1, six-hour task timeout, zero immediate task retries (next hourly scan retries failures). These settings are a proposal, not deployed configuration. A global Cloud Storage generation-conditional seven-hour lease rejects overlapping jobs; do not increase task timeout or launch multiple worker implementations without reviewing the lease. An abruptly killed execution can delay recovery until that lease expires; normal failures release it immediately. Hourly polling intentionally tolerates completion latency to reduce costs. A video can wait roughly two hourly scans after it stops changing; additional channel live time also delays new downloads.

The small bucket holds durable JSON state plus temporary full media, not a second permanent video archive. It is necessary here to let Drive retry without another Twitch download and to avoid keeping a long video in Cloud Run's memory-backed filesystem. Streaming yt-dlp → FFmpeg → 8 MiB GCS writes bounds Python buffering independently of VOD length; the proposed 1 GiB memory still requires measuring native process usage on actual long VODs. Temporary bytes are deleted only after durable, checksum-verified Drive completion. No automatic lifecycle rule deletes state or unfinished media. Failed/orphan stage objects can accrue charges; monitor and review them before deletion. Proposed daily alert for unfinished staging older than 24 hours and a measured storage budget; monitoring is not yet installed.

Cloud Storage is a small additional paid service; existing Drive quota stores the final archive. This design minimizes idle compute/disk costs and favors retry reliability over the absolute minimum per-byte cost. Actual cheapest architecture depends on monthly volume and transfer charges. A direct Twitch-to-Drive pipe can reduce staging charges but cannot reliably retry an upload without re-fetching a large VOD; that is not this implementation.

## Detection and completion rules

Helix Get Users resolves MrHype420 to an immutable numeric user ID each execution. Get Streams tests whether the owner is offline; Get Videos paginates `type=archive` results. The implementation scans all available pages up to 10,000 entries, failing rather than silently truncating beyond the cap. It ignores highlights/clips, other owners, and video creation times earlier than the explicitly chosen `ARCHIVE_SINCE` cutoff. Select that cutoff before enabling; use an earlier date to include the supplied test VOD if needed. No ID or creation timestamp has been invented for the supplied video.

For a new VOD, persist its duration, observe it unchanged on another execution at least ten minutes later, require owner offline, then require yt-dlp's matching owner, VOD ID, known `is_live=false`, and matching duration. Helix does not expose a definitive finalized/download-ready flag; these are conservative completion heuristics, not a Twitch completion guarantee. Growing or processing metadata defers work rather than marking success. API errors fail the job; 401, 429 and transient API failures retry on the next schedule. API tokens are acquired freshly for each job, so no expired-token loop across executions. Two-phase staging already validated can finish uploading while the owner is live again.

The cutoff is an intentional first-run backfill control, not a substitute for durable deduplication. Keep state records indefinitely unless explicitly migrating them. A saved VOD may expire or be removed before successful staging; alert on failed executions and resolve quickly. Nothing can recover audio or video Twitch no longer provides.

## Download compatibility, full video and audio

The official [Get Videos API](https://dev.twitch.tv/docs/api/reference/#get-videos) supplies metadata, not a general VOD video-file download endpoint. The worker uses **yt-dlp 2026.10.26**'s [TwitchVodIE](https://github.com/yt-dlp/yt-dlp/blob/2026.10.26/yt_dlp/extractor/twitch.py): playback metadata/token requests and HLS extraction. This is a maintained third-party extractor using Twitch playback interfaces; its presence was verified in that pinned release, but the supplied VOD's actual extraction is **not yet verified**. Twitch can change those interfaces or restrict access. Do not claim official API download support.

The downloader explicitly selects yt-dlp’s native HLS downloader so fragment retry/failure settings apply, then selects a full combined video+audio rendition, requests the whole VOD with no time range, retries fragments, and aborts on an unavailable fragment instead of silently skipping it. FFmpeg copies the streams, explicitly converts ADTS AAC framing for MP4, and produces a single fragmented MP4 without transcoding or splitting. This is one playable file, not separate archive segments. Fragmented MP4 supports a non-seekable output stream; Google Drive preview support must be checked separately from normal-player compatibility. No claim of preview support is made.

Source and FFmpeg must both exit successfully, an audio and a video stream are mandatory, and FFmpeg must report completion and duration within 0.5–5 seconds of expected duration (strict absolute maximum five seconds, not a percentage that loses minutes on long streams). Bytes and MD5 are computed during staging. This rejects truncation and missing tracks; it cannot prove that all speech or every source frame is present. The owner-confirmed VOD microphone should be preserved if present in the selected source audio. Muted portions and absent broadcast audio cannot be restored. Check future Xbox/VOD audio settings and listen to the final test copy.

A long stream is not constrained by local disk size. Transfers must fit the six-hour **processing** timeout; download need not run at playback speed. If measurement shows a full transfer exceeds that timeout, review a larger timeout plus lease or a resumable fragment-download design before enabling for those workloads. Do not repeatedly bill a job that cannot finish. Five TB/file and user upload/storage quotas can still prevent a one-file upload; this worker fails and retains staging rather than silently splitting or reducing quality.

## Durable retries and duplicate prevention

A global generation-conditioned GCS lease serializes scheduled executions. Per-VOD JSON stores stable observations, a **preallocated Drive file ID**, validated staging generation/size/MD5, and completion. The ID is persisted before create; expected checksum is persisted before any Drive upload. Retries query that same ID. A successful upload followed by a timeout or process crash is recognized and verified on the next run rather than creating a second file. Drive display names alone are never used for deduplication.

Uploads use seekable, generation-pinned GCS range reads through the Google Drive client, resumable 8 MiB chunks, request timeouts, and exponential request retries. Within an attempt, client retries can resume transfer. After process death, a not-yet-committed upload may restart from the staged object with the same preallocated ID; persistent resumable session URLs are deliberately not stored as bearer secrets. No second Twitch download is needed once validated media metadata is saved. A crash before that save can re-download and overwrite orphan staging on the next attempt.

Remote file must match expected MD5, size, destination parent, VOD ID and channel appProperties, and must not be trashed. Save completion durably before deleting the pinned staging generation; cleanup itself is idempotent after a crash. A mismatching or deleted remote archive needs operator review; a journaled completion is not continually reconciled against user deletion. No auto-restore or auto-delete in Drive, no sharing changes. Corrupted/missing state is an incident: do not clear it and rerun blindly, since its preallocated IDs enforce deduplication.

## Cost model and comparison

Pricing reviewed November 1, 2026; estimates below are illustrative USD list prices, not a billing guarantee. For the proposed 1-vCPU/1-GiB job in us-central1, [Cloud Run Jobs](https://cloud.google.com/run/pricing) lists $0.000018/vCPU-second plus $0.000002/GiB-second, about **$0.072 per running hour before free tier**, with one minute minimum per execution. 720 no-work hourly executions at the minimum cost about **$0.864/month before free tier**; ten additional transfer hours add about **$0.72** compute. The shared free-tier allowance can cover those example compute totals if unused by other projects; do not assume eligibility or availability.

[Cloud Scheduler](https://cloud.google.com/scheduler/pricing) lists **$0.10/job per 31 days** before applicable free allowances. Add [Cloud Storage](https://cloud.google.com/storage/pricing) temporary GiB-hours and operations, secrets, image/build storage, logs, and network charges. Same-region placement avoids unnecessary cross-region staging traffic. Cloud-to-Drive traffic must be priced explicitly against the applicable Google destination/network classification; this proposal does **not** assume free egress. At 6 Mb/s, a four-hour VOD is roughly 10.8 GB before container overhead. Repeated failed transfers can dominate compute/storage/network costs. New GCS buckets may enable soft-delete retention; inspect and, only with approval, configure temporary media retention/soft delete to avoid retaining charged deleted videos unintentionally. Do not apply lifecycle deletion to `state/`.

Always-on VM alternative incurs 730 running hours plus persistent disk/public-IP/egress charges regardless of new VODs; it is no longer the recommended starting point. GitHub scheduled Actions can have unused free allowances but introduce runner storage/time limits, scheduling delays and another location for OAuth secrets; they are not selected as the production transfer host. Obtain actual volume and price network transfer before claiming a fixed monthly bill. Budget alerts notify; they are not a hard spending cap. No paid service was enabled, built or deployed here.

If this particular VOD is login/subscriber-restricted, stop and obtain explicit approval for owner-authenticated extraction; no restriction bypass or cookies are implemented.
2. **Owner Google Drive OAuth:** offline authorization for exactly `https://www.googleapis.com/auth/drive.file` using the existing OAuth client, plus an app-specific per-file grant for the **existing folder** (normally owner selection through Google Picker using the same client). A folder ID is not authorization. The secure Picker/consent bootstrap still needs implementation against the actual existing client type, redirect origins, and consent status. Inspect first; do not change scopes/redirects/publishing without approval. Worker rejects broader stored scopes. Store an `authorized_user` refresh credential as a secret, not a service-account key. Confirm token refresh longevity; external apps left in OAuth Testing can have seven-day refresh-token expiry for these scopes. Drive API must be enabled only after approval if currently off.

CDN hosts are dynamic; review observed names rather than opening arbitrary egress. No credentials are currently configured here.

No new Twitch broadcaster user OAuth grant is required for the public path. No Google-wide `drive` scope, account password, service-account key, public deployment, Firebase deployment enablement or merge is requested by this implementation. ## Safe verification and rollout

Offline: `python -m unittest discover -s tests -v` with FFmpeg/ffprobe. These tests need no API credentials.

After approved network access and installing requirements, metadata-only playback compatibility test (no Drive/cloud write):

```sh
python -m recorder.check_vod --vod-id 2917078189
```

Authorized full video/audio test to an adequately sized scratch disk (no upload):

```sh
python -m recorder.check_vod --vod-id 2917078189 --output work/MrHype420-2917078189.mp4
```

That command uses exclusive creation, does not overwrite files, and checks full-file duration plus audio/video presence. Failed downloads may leave a partial local file; inspect/remove it before retry. Never use a partial test file as proof of success. It is an explicit test tool, not the production home-computer dependency.

After provisioning and owner Drive consent are separately approved: inspect the private bucket/secret/IAM/job settings, keep ARCHIVE_ENABLED=false until review, select ARCHIVE_SINCE to include the test VOD, then approve a single controlled job limited by `--vod-id 2917078189`. Confirm source duration/owner, final MD5/size/parent, one file, listening for game/microphone audio, and no second file on rerun. Exercise network interruption, ambiguous Drive completion, revoked token, low quota, crash/lease expiry and long VOD. Validate memory/time and install failed-execution/backlog/cost alerts before hourly unattended operation. The worker code does not create its Scheduler, bucket, identities, secrets, alerts, or OAuth grant.
